# Retail Reliability Lab

一个面向学习和作品集的 Kubernetes 可靠性工程实验项目：围绕 AWS Retail Store Sample App v1.6.2，练习有状态业务系统的自动化交付、可观测性、备份恢复、故障诊断和发布回滚。

## 项目目标

把“应用能跑”推进到“变化可控、故障可解释、数据可恢复”：

1. 固定上游版本，能够在本机 Kubernetes 集群重复部署。
2. 用 CI 验证清单、镜像和基础测试，再由 GitOps 管理集群期望状态。
3. 建立从指标、日志、事件到告警诊断 Agent 的证据链。
4. 对数据库和持久化数据做可验证的备份、恢复和恢复演练。
5. 用故障评测集衡量诊断 Agent 的定位、证据引用和建议质量。

## 交付闸门

| 闸门 | 目标 | 必须留下的证据 |
| --- | --- | --- |
| G0 基线 | 记录节点、命名空间、StorageClass、PVC 和 Pod 状态 | `evidence/` 中的脱敏快照 |
| G1 可复现部署 | 应用版本和依赖固定，部署结果可重复 | 版本清单、部署日志、访问验证 |
| G2 自动化验证 | 静态检查、清单校验、冒烟测试进入 CI | CI 运行记录和失败样例 |
| G3 GitOps | Git 变更可同步到集群，错误变更可回滚 | 同步记录、回滚记录 |
| G4 可观测性 | 关键指标、日志、事件和告警具有关联性 | 告警规则、截图或导出结果 |
| G5 数据恢复 | 备份可读、恢复可用，且在隔离环境演练过 | 备份校验和恢复报告 |
| G6 故障评测 | Agent 能针对标准故障给出证据约束的诊断 | `tests/` 评测结果、事件复盘 |

## 目录结构

```text
retail-reliability-lab/
├── backup/              # 备份、恢复和数据一致性演练
├── docs/
│   └── incidents/       # 事件记录和复盘模板
├── evidence/            # 脱敏后的验证结果；原始敏感材料不入库
├── infra/vendor/        # 锁定的上游清单、版本和校验信息
├── monitoring/          # 指标、日志、告警和诊断 Agent 设计
├── scripts/             # 可重复执行的安全辅助脚本
└── tests/               # 冒烟、恢复和故障评测
```

## 当前边界

- 这是本机/实验室集群项目，不代表生产级高可用方案。
- `local-path` 一类存储通常是节点本地盘；节点故障时不能自动提供跨节点高可用。
- 不提交 kubeconfig、Token、云凭据、Cookie、私有日志或未经脱敏的业务数据。
- 不使用 `latest` 标签；上游应用、镜像和工具版本都应可追溯。
- 破坏性操作必须限定命名空间和资源范围，并在操作前保留基线证据。

## 学习顺序

先完成 G0，确认集群的 StorageClass 和 PVC 能力，再进入应用部署。若集群没有 StorageClass，依赖 PVC 的工作负载可能长期处于 `Pending`，这不是应用代码故障，而是存储供给链没有接上。具体判断方法见 [`docs/OPERATIONS.md`](docs/OPERATIONS.md)。

后续每一步都要求同时提交三类内容：配置、验证命令、验证结果。这样仓库记录的是“为什么这样做以及如何证明它有效”，而不只是 YAML 文件。

## 上游项目

本项目学习使用 AWS Retail Store Sample App，并将部署版本固定为 `v1.6.2`。上游代码和许可证仍归原项目所有；本仓库只保存实验所需的锁定信息、补丁、验证记录和运维资产。
