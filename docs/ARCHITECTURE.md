# 架构与责任边界

## 逻辑链路

```text
开发者提交
    │
    ▼
GitHub ── CI: 清单校验 / 安全检查 / 冒烟测试
    │
    ▼
GitOps 控制器 ── 期望状态同步 ──> Kubernetes 集群
                                      │
                   ┌──────────────────┼──────────────────┐
                   ▼                  ▼                  ▼
              无状态服务          有状态服务           观测组件
                   │                  │                  │
                   └──────────> 指标 / 日志 / 事件 <─────┘
                                      │
                                      ▼
                             告警诊断 Agent
                                      │
                                      ▼
                             证据、结论、建议
```

## 分层说明

### 应用层

Retail Store Sample App 提供电商业务流量和多服务依赖。应用版本、镜像来源和配置必须在 `infra/vendor/` 或后续明确的部署目录中锁定，避免集群状态依赖人工临时修改。

### 交付层

- CI 负责“提交是否合格”。
- GitOps 负责“集群是否达到 Git 中声明的状态”。
- 回滚的第一选择是恢复到已知可用的 Git 版本，而不是直接在集群中手工改回去。

### 数据层

有状态组件通过 PVC 获得存储。StorageClass 决定 PVC 如何动态供应；没有 StorageClass 时，PVC 通常不能自动绑定。实验集群可以使用节点本地存储，但必须把它的非高可用属性写进风险说明。

### 观测与诊断层

告警诊断 Agent 只能基于时间窗口内的指标、日志、Kubernetes 事件、变更记录和依赖状态作结论。每个结论都应能回指证据，不能只输出“可能是网络问题”这类不可验证的猜测。

## 关键设计决策

1. 上游版本固定为 `v1.6.2`，升级必须形成独立变更和回归证据。
2. 数据恢复先在隔离命名空间验证，再考虑覆盖原工作负载。
3. 故障注入只允许在实验命名空间进行，并记录开始时间、结束时间和清理动作。
4. 运行状态不直接当作事实写入文档；集群快照和命令输出放入 `evidence/`，并先脱敏。
