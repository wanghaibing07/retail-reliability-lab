# 先用中文看懂这个项目

这页面向自己复习和第一次看项目的人。先理解做过什么，再记工具名称；面试时只使用自己能解释、能指向证据的表述。

## 一句话

我用 AWS 提供的电商样例搭建了一个三节点 Kubernetes 运维实验室，练习并验证自动部署、监控告警、数据库恢复、发布失败恢复和性能测试。

## 60 秒人话版

这个项目的业务代码来自 AWS，我主要做运维和可靠性验证。

一开始，我排查镜像下载异常，把部署和检查过程写成脚本。后来让代码修改先经过自动检查，再由 Argo CD 按 Git 中的配置部署到集群，验证手工改动能被自动纠正。

监控方面，我验证了告警从触发到恢复的邮件通知；数据方面，我实际恢复过订单数据库，并确认应用能读回订单。我还故意让新版本无法通过就绪检查，观察旧实例继续服务，再通过撤销 Git 中的错误配置恢复。

最后做只读浏览性能测试：每秒 30 个 HTTP 请求持续 300 秒的运行点已验证健康；每秒 45 个请求时多次出现阶段性退化，后段又恢复。所以我没有把 45 当成最大容量，也没有在证据不充分时乱调参数。

## 工具和术语对照

| 名称 | 中文理解 | 本项目中的具体用途 |
| --- | --- | --- |
| Linux / Shell | 操作系统与命令行脚本 | 查网络、进程和资源，编写部署、验证与备份脚本 |
| Kubernetes / K8s | 管理容器应用的平台 | 在三台虚拟机上运行多服务样例 |
| Pod | Kubernetes 管理的最小运行单元，可包含一个或多个容器 | 承载 UI、订单等服务；运行中不代表已能接流量 |
| Ready / readiness | 就绪状态 / 就绪检查 | 判断实例当前是否适合接收服务流量 |
| liveness | 存活检查 | 检查失败达到阈值后可触发容器重启；不同于就绪检查 |
| Service / EndpointSlice | 稳定服务入口 / 后端端点记录 | 了解请求如何找到合适的 Pod |
| replica / rollout | 实例副本 / 滚动发布 | 更新时保留旧健康实例，观察新实例状态 |
| CI / GitHub Actions | 提交代码后的自动检查 | 检查脚本语法、ShellCheck 和配置结构；不能证明运行时一定健康 |
| PR | 合并请求 | 先展示改动和检查结果，再合并到主分支 |
| GitOps / Argo CD | 用 Git 中的配置驱动部署 / 执行它的工具 | Git 记录期望状态，Argo 持续核对并同步集群 |
| desired state | 期望状态 | 例如 Git 写 2 个副本，集群应向这个配置收敛 |
| Auto Sync / Self Heal | 自动同步 / 自动纠正偏差 | Git 更新后部署；手工改成 1 副本后恢复为 Git 声明的 2 个 |
| Prune | 清理 Git 已删除的资源 | 用临时配置资源验证清理；数据库等有状态资源另设保护 |
| Git revert | 在 Git 中提交一次反向修改 | 撤销坏配置，让自动部署恢复期望状态 |
| Prometheus | 指标采集与查询工具 | 查询请求、错误、延迟、容器和主机资源等证据 |
| Alertmanager | 告警处理与通知工具 | 接收告警并发送触发、恢复邮件 |
| Blackbox / black-box | 从外部探测 / 黑盒观测 | 检查 UI 的 HTTP 响应；关注用户入口表现 |
| white-box | 查看内部状态的白盒观测 | 查看应用指标、Pod 状态和资源压力，辅助解释外部异常 |
| firing / resolved | 告警触发 / 告警恢复 | 已用受控探测判据演练验证两种邮件，不等于生产事故 |
| RED | 请求量、错误、耗时 | 先看用户请求的表现 |
| USE | 资源使用率、饱和度、错误 | 再看系统资源压力；有相关性仍不等于找到了根因 |
| PostgreSQL / pg_dump / pg_restore | 数据库 / 导出备份 / 恢复工具 | 只针对 Orders 订单数据库验证恢复能力 |
| SHA256 | 文件摘要校验 | 核对备份文件是否一致；还需要实际恢复和读回数据 |
| PVC / Retain | 持久存储申请 / 保留策略 | 保存订单数据；不提供跨节点复制或完整灾备 |
| Artillery / VU | 压测工具 / 虚拟用户 | 一个虚拟用户可能发多个请求，用户数不等于请求数 |
| RPS | 每秒 HTTP 请求数 | 30 RPS / 300 秒是固定只读负载下的已验证健康运行点 |
| p95 / p99 | 95% / 99% 样本不超过的耗时 | 只在同一请求范围、统计窗口内比较延迟 |
| episodic degradation | 阶段性退化，时好时坏 | 45 RPS 多轮出现超时或延迟突增，后段恢复 |
| exact knee / maximum capacity | 精确性能拐点 / 最大容量 | 两者尚未确定；不能把 30 或 45 写成最大容量 |
| INVALID / NOT_STARTED | 证据不足而无效 / 尚未开始 | 前者是结果资格；后者是生命周期，不能混作“实验失败” |
| HA / DR | 高可用 / 灾难恢复 | 本实验室没有证明生产级高可用或完整灾备 |

## 在深圳投递时怎么用

1. 先读本页，再按岗位从 [简历条目](resume-bullets.md) 选择三到五条。
2. 用上面的 60 秒版本讲项目，能讲清后再展开 [三分钟版本](interview-guide.md)。
3. 优先准备 [真实排障、监控、恢复与发布故事](incident-stories.md)，再练 [面试题库](interview-question-bank.md) 的 12 道优先题。
4. 任何数字和“我做了什么”的表述，最后对照 [声明边界](claim-boundaries.md)。说不清的部分先回到证据，不硬背工具名称。

原始技术记录保留必要的英文名称、命令和状态字段，便于核验；本页提供中文阅读入口，不改变实验结论。
