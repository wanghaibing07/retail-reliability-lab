# Retail Reliability Lab 项目概况

基于 AWS Retail Store Sample App v1.6.2 搭建的三节点 Kubernetes 可靠性工程实验室，围绕部署交付、监控告警、数据恢复、发布安全和容量测试开展验证。

业务应用采用 AWS 的电商微服务样例，包含 UI、商品目录、购物车、结算、订单及各自的数据依赖。我负责部署与监控配置、自动化脚本、故障排查和验证记录。

## 部署和检查

最初部署时，镜像下载会出现超时和连接异常。我分别检查 DNS 解析、HTTPS 连接和 containerd 容器运行时，再对比串行、并发拉取镜像的情况。最后把镜像预拉取从部署中拆出来，先准备镜像，再部署应用。[排查记录](../incidents/001-image-pull-failure/README.md)

随后把部署、检查和销毁写成 Shell 脚本，做了两次完整重建。检查不只看 Pod 是否在运行，还确认实例已就绪、Service 有可用后端、业务入口返回 HTTP 200。[部署脚本](../../scripts/deploy.sh) · [检查脚本](../../scripts/verify.sh)

## 用 Git 管理配置

部署配置保存在 Git 中。修改先经过 GitHub Actions 检查脚本和配置结构，再由 Argo CD 同步到集群。这样能查到每次配置修改，也能通过 Git 撤销错误改动。

我做过一次偏差测试：Git 中写着两个 UI 副本，手工把集群改成一个，Argo CD 随后把它恢复为两个。这就是这里所说的“自愈”：纠正配置偏差。它不会自动修复业务代码里的错误。资源清理另用临时 ConfigMap 做了测试，数据库等有状态资源设置了删除确认。[GitOps 记录](../gitops/stage3-gitops.md)

## 监控和发布演练

Prometheus 采集指标，Blackbox 从外部访问 UI，Alertmanager 发送通知。为检查邮件链路，我临时让探测器只接受 HTTP 418。首页仍然返回 200，但探测被判为失败，告警邮件随之触发；恢复原判据后，收到了恢复邮件。这次演练没有停业务。[告警记录](../observability/stage4-metric-driven-alert-drill.md)

发布演练则故意把新 UI 实例的就绪检查地址改错。自动检查通过了，但新实例运行后无法就绪，不能作为可用后端接流量。旧的两个健康实例继续服务，发布停滞触发告警。我在 Git 中撤销错误配置，再由 Argo CD 同步恢复。[发布演练记录](../releases/stage6-closeout.md)

## 订单数据库恢复

订单数据库最初使用临时目录，Pod 被删除后有丢失数据的风险。我先备份 PostgreSQL，把备份恢复到另一节点上的隔离数据库，再通过数据库查询和 Orders API 读回订单。

确认备份可用后，在暂停写入的维护窗口迁移到持久存储。之后分别检查旧订单和新订单，重建数据库 Pod，再检查一次，两条记录都还在。备份副本离开了源虚拟机，但仍在同一台物理宿主上；这次只验证了订单数据库的恢复，不是异地灾备。[备份与恢复记录](../backup/stage5-closeout.md)

## 性能测试测到了什么

用 Artillery 模拟只读浏览请求，同时查看 Prometheus 中的请求、错误、延迟和资源指标。这里的 RPS 是每秒 HTTP 请求数，不是在线人数。

30 RPS 持续 300 秒的运行点已验证健康。45 RPS 在多轮测试中出现超时或延迟突增，但后段又恢复了，所以还不能把它当成硬上限。39 RPS 没有取得有效资格结论：有的记录缺少必要的测试后检查，有的在预热时就中断，还有一次只准备了脚本。

这轮没有确定精确性能拐点或最大容量。资源压力与超时同时出现，也不足以证明某个服务就是唯一瓶颈，因此最终没有新增系统调参。[性能测试报告](../performance/stage7-closeout.md)

| HA / DR | 高可用 / 灾难恢复 | 本实验室没有证明生产级高可用或完整灾备 |
